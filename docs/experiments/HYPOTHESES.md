# Приоритетные гипотезы — реестр v1

Статус всех гипотез: **зарегистрированы, эффект на train/validation ещё не измерен**. Подтверждённый дефект реализации не равен доказанной пользе предложенного исправления. Основания перечислены в [AUDIT.md](AUDIT.md); правила расчёта метрик и stop rules — в [FROZEN_PROTOCOL.md](FROZEN_PROTOCOL.md).

Реестр конечный: 7 гипотез, 5 экспериментов. P0 — следующий causal B2; P1 — отдельная итерация после него. Успех оценивается на grouped train CV; validation служит единственной описательной проверкой уже зафиксированного кандидата. Все пороги ниже — заранее выбранные критерии эксперимента, не заявленные характеристики оборудования.

## Пять исполнимых опытов

**E1 — обязательная основа B2.** Сначала логические проверки, затем quality-only кандидат на train. Минимум: sparse normal, sparse sustained anomaly, sparse frozen values с пропущенным update, dense frozen values, полный gateway gap, channel-only gap, gap до конца replay, восстановление, смешение двух причин подряд. Labels тестовых fixtures заданы их построением и не считаются новыми наблюдениями benchmark.

**E2 — диагностический прирост B2.** Только после E1. Проверить отдельно SENSOR_DRIFT vs SENSOR_CALIBRATION_SHIFT vs SENSOR_NOISE_SPIKES, правильный канал и confusion с MACHINE. При отсутствии свежих согласующих каналов использовать UNKNOWN. Не менять одновременно reference и режимную модель: это лишит сравнение интерпретируемости.

**E3 — nuisance и честная неопределённость.** После B2, отдельный freeze. Отчёт должен показать, какие тревоги перестали быть конкретным диагнозом, сохранились ли anomaly alerts и что произошло с настоящими fault events. Validation nuisance уже известен, поэтому нельзя создавать специальное правило для него.

**E4 — холодный старт.** После B2, отдельный freeze. Исходные pre_existing события train дают естественную проверку загрязнённой опоры. Сравнивать wall-clock delays и число пропусков, а не только lead среди удачных случаев. Prior строится на остальных train активах; никакого извлечения здорового контрфактуала из симулятора для deployment.

**E5 — демонстрация пользы датчика.** На выбранной по train версии: для каждой из трёх групп original/mask/restore; маска удаляет mean/std/min/max/count, waveform и производные признаки этой группы, а availability metadata отражает отсутствие. `rows` gateway не изменяется из-за удаления одного прибора. Mask с начала окна, отдельный replay каждой ветви; нельзя сохранить full-sensor reference внутри masked ветви. Без переобучения/перенастройки между ветвями — измеряется зависимость фиксированного алгоритма от информации. Если позже нужен retrained masked model, это отдельный опыт с отдельным train-only freeze.

Остановка: после B2 v1 не превращать эту таблицу в бесконечный поиск. Для E3/E4 до запуска нужны конкретные candidate configs и новый train-only manifest. При нехватке времени статус «не выполнено» лучше неподтверждённого результата.
